# ADR 0002: 素材を 3 種類（Markdown・手順 JSON・メニュー定義 JSON）に分け、操作経路は参照名で解決する

- 状態: 提案

## 文脈

既存の PDF 版マニュアル（統合版）は、文章中心の原稿、画面操作の手順書、業務システムのメニュー一覧という
性格の違う 3 種類の内容から成る。手順書と一覧には「ボタンの並び（F10 オプション1 › F1 薬品在庫 › …）」が
多数現れ、ボタンの絵柄・キー・ラベルは 1 か所で管理したい。

素材の持ち方として次の案があった。

1. **すべて Markdown** にし、ボタンの並びも画像タグや HTML で原稿に直接書く
2. **Markdown + 手順 JSON + メニュー定義 JSON** に分け、ボタンは参照名（`メニューID:キー`）で指す
3. 専用のエディタ UI でマニュアルを構造化データとして編集する

## 決定

**案 2** を採る。

- Markdown は原稿として従来どおり書く。front matter（`title` / `subtitle`）と `[[chips:ref, ref]]` 記法、
  クラス付き `div` の生 HTML（フロー図・出典行・要確認枠）を許容する
- 手順書は `title` / `purpose` / `steps[].text` / `steps[].ui`（参照名の並び）/ `cautions` を持つ JSON とする
- メニュー定義は `menus[].items[]`（`ref`・`key`・`label`・`opens`・`pict`）と `screens[].fkeys[]` を持つ JSON とし、
  参照名 `m_xxx:F1`（メニュー項目）と `s:画面名:F12`（画面のファンクションキー）を解決する唯一の表とする
- 「メニュー構成とアイコン一覧」の章は、このメニュー定義とツリー表示テキストから自動生成する
- 絵柄は PNG を data URI で埋め込む。絵柄の照合はファイル名のみ（パス不問）で行う
- 統合版（表紙・全体目次・章バッジ）は章の「グループ名」で組み立てる。章の順序は利用者が決める

## 結果

- 利点: ボタンの表記ゆれが無くなる。メニュー定義を直せば全章に反映される。手順書は JSON なので
  将来の構造化（検索・翻訳・別フォーマット出力）に向く。原稿は Markdown のまま読み書きできる
- 欠点: 参照名を覚える必要がある（未登録はチップが赤枠になり警告で気づける）。生 HTML を許容するため、
  DOMPurify の許可範囲（`div` + `class`）に依存する
- 補足: 参考 PDF の「原本：…」の行や章タイトルの言い換えなど、素材に無い情報は CLI の manifest
  （または手順 JSON の `source` / `sub`）で補う
